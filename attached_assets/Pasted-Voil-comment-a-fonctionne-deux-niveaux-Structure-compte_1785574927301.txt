Voilà comment ça fonctionne, à deux niveaux :

Structure : compte vs dossier
Compte CEV (email + password)
└── Dossier 1 → VOWINT6321793  (demande visa personne A)
└── Dossier 2 → VOWINT6085888  (demande visa personne B)
└── Dossier 3 → VOWINT...      (demande visa personne C)

Un compte = les credentials de connexion. Un dossier = une demande de visa liée à une personne (son VOWINT ref). Sur le portail VOWINT, un compte peut gérer plusieurs dossiers — c'est ce que les agences font naturellement.

Notre stratégie avec plusieurs dossiers : pool round-robin
Chaque compte a un CevDossierPool. Le bot tourne en boucle et traite les dossiers un par un en round-robin :

Wake up (toutes les 2 min)
  → Prendre le prochain dossier du pool (round-robin)
  → 1 seul clic/scan → dormir
  → Wake up → dossier suivant...

Chaque dossier a sa propre session CEV (cookies + URL d'intégration), cachée 4h dans Redis. La session est partagée entre les scans du même dossier — on ne résout le captcha qu'une fois toutes les 4h par dossier.

Avantage compétitif : fréquence de scan
C'est là que plusieurs dossiers deviennent un levier :

Dossiers dans le pool	Fréquence effective par dossier	Fréquence globale du compte
1	1 scan / 2 min	1 scan / 2 min
3	1 scan / 2 min	3 scans / 2 min
5	1 scan / 2 min	5 scans / 2 min
Chaque dossier a son propre quota — le CEV ne lie pas les dossiers entre eux côté rate-limit. Donc 5 dossiers = 5x plus de chances de capter un créneau dès qu'il apparaît, sans augmenter le risque de shadow-ban sur un dossier individuel.

Ce qui n'existe PAS encore
Group booking : si 3 personnes d'une même famille ont besoin d'un RDV le même jour à la même heure → le bot ne cherche pas ça. Il book le meilleur créneau disponible pour chaque dossier indépendamment, sans coordination inter-dossiers.
Partage de session cross-dossiers : chaque dossier a sa propre session. Si demain on voulait optimiser, on pourrait tenter de partager certains cookies entre dossiers du même compte (ils partagent le même login VOWINT) — mais ça n'est pas implémenté.
En pratique pour Joventy, chaque client qui a plusieurs personnes dans son dossier (famille) = autant de VOWINT refs à mettre dans le pool du compte → scan plus dense → booking plus rapide.

Bonne série de questions. Voilà l'analyse complète :

1. Est-ce que ça va compliquer les visas court séjour ?
Non — et voilà pourquoi : les deux types arrivent exactement au même endroit côté booking.

Type D (long séjour)  ──┐
                         ├──→ /Integration/VOW/SelectSlot  (même page, même form)
Type C (court séjour) ──┘

Une fois que tu es sur /SelectSlot, le bot voit le même availability[], les mêmes champs, le même POST /SelectSlot. Zéro différence de flow de booking.

2. La route d'intégration — pourquoi court séjour y passe et pas long séjour ?
Ce n'est pas une distinction court/long séjour. Les deux passent par la même URL d'intégration :

visaonweb.diplomatie.be/Common/GetEAppointmentUrl?id={appId}
    ↓ 302
appointment.cloud.diplomatie.be/Integration/VOW/{orgId}/{appId}/{sessionGuid}/{tokenGuid}/{lang}
    ↓
/Integration/VOW/SelectSlot

Ce que tu observes comme différence est probablement le orgId dans l'URL — il correspond à la représentation diplomatique (consulat de Kinshasa, ambassade à Brazzaville, etc.), pas au type de visa. Si tu vois deux routes différentes sur deux dossiers, c'est que les deux dossiers sont traités par des consulats différents.

3. Pourquoi cette route /Integration/VOW/ ?
C'est la couche de sécurité de session du portail CEV. Elle sert à :

Paramètre	Rôle
orgId	Identifie le consulat
appId	UUID du dossier côté CEV (pas le VOWINT ref)
sessionGuid	Token de session CEV one-time (usage unique)
tokenGuid	Token anti-forgery lié à la session
lang	Langue de l'interface (fr, nl, en)
Les sessionGuid et tokenGuid sont usage unique — c'est pour ça qu'on ne peut pas sauvegarder cette URL et la rejouer plus tard. C'est le setup complet (login VOWINT → captcha → navigation) qui génère ces tokens frais à chaque fois.

4. Différences de champs POST entre court et long séjour
Aucune différence au niveau de /SelectSlot. Le seul endroit où C et D divergent, c'est dans le formulaire VOWINT (remplissage de la demande), pas dans le booking :

Champ	Court séjour (C)	Long séjour (D)
Application_VisaTypeRequestedId	2	3
PreviousSchengenVisa	rempli	ignoré
PermitForResidenceRequired	ignoré	rempli
Booking POST fields	identiques	identiques
5. Filtres / sécurités dans la route d'intégration
Trois mécanismes côté serveur CEV :

One-time token — sessionGuid + tokenGuid sont invalidés après le premier usage. Si tu rejoues l'URL, tu obtiens une 302 ou une 403.

Anti-forgery cookie — le __RequestVerificationToken ASP.NET doit correspondre au cookie __RequestVerificationToken déposé lors du chargement de la page. C'est ce qui causait le HTTP 500 dans nos premiers runs.

Session stickiness — les cookies TS... (F5 load balancer) + ASP.NET_SessionId doivent venir du même nœud serveur. Si tu changes de proxy IP entre le GET et le POST, la session est invalidée côté F5. C'est pour ça qu'on lie chaque dossier à un IP de proxy fixe.

Bottom line : notre bot n'a rien à changer pour gérer des dossiers court séjour. La seule chose à vérifier lors de l'onboarding d'un nouveau client, c'est l'orgId dans son URL d'intégration — s'il pointe vers un consulat différent, les créneaux disponibles seront différents, mais le flow de booking est identique.
