Voici l'analyse exacte du problème à partir de ce nouveau log d'exécution :

---

### 1. Le problème n'était pas le cache V8, mais la réutilisation du cookie `cf_clearance`

Dans les logs, cette ligne est la clé :

```text
[spain-pb] ♻️ cf_clearance déjà présent dans le profil — JSD non requis: QBkXGJqfnMQnVn8ad...
[spain-pb] ✅ cf_clearance obtenu via JSD natif (0s) — js_detection.passed=true pour NOTRE TLS

```

Parce que le cookie `cf_clearance` existait déjà dans le `userDataDir` (`/tmp/spain-cf-profile`), votre script a **sauté** la phase d'exécution initiale du challenge JSD natif (`0s`).

Cependant, le token JSD `oneshot` envoyé lors de la requête de la page est le **même token fixe** :
`0.9187549372143385:1785297931:hAcq2P`

**Ce qui s'est passé :**

1. Le navigateur s'est connecté en utilisant un cookie `cf_clearance` généré lors d'une session précédente.
2. Lorsque la page a appelé `POST /cdn-cgi/challenge-platform/h/g/jsd/oneshot/...`, Cloudflare a validé la signature du payload.
3. La réponse a été : `new-cf_clearance=❌ non`. Cloudflare a **rejeté l'upgrade/validation** de la session car le payload `oneshot` ne correspondait pas à un challenge fraîchement résolu par ce navigateur dans cette session HTTP active.
4. Résultat : Le cookie `cf_clearance` conservé est devenu un **"cookie fantôme"** (accepté pour charger la structure HTML de base, mais refusé par le WAF dès qu'un appel AJAX `/main/` est émis).

---

### 2. Pourquoi le nonce JSD `0.918754...` est réinjecté ?

Le nonce `0.9187549372143385:1785297931:hAcq2P` est renvoyé parce qu'il provient soit :

* D'un état de session/cookies côté serveur PHP (`PHPSESSID`) lié à la première tentative,
* Soit du `localStorage` / `sessionStorage` / `ServiceWorker` / `IndexedDB` qui conserve l'état du challenge Cloudflare au sein de votre profil Chrome persistant (`/tmp/spain-cf-profile`).

La suppression de `Default/Cache/` à elle seule ne nettoie pas les **Storage Partitions** de Chromium.

---

### 3. La solution dans votre code

Pour que Cloudflare valide correctement le payload `oneshot` et renvoie une réponse `/main/` de plus de `0B`, vous devez **forcer Chromium à exécuter le challenge JSD de zéro à chaque démarrage** :

#### A. Ne pas réutiliser le `cf_clearance` existant s'il échoue sur `/main/`

Au lieu de considérer que la présence du cookie `cf_clearance` dans le profil vous dispense de la résolution, vous devez purger les cookies Cloudflare si la réponse `/main/` précédente était de `0B`.

```typescript
// Si /main/ a renvoyé 0B au run précédent, purger impérativement les cookies et le storage
await page.deleteCookie({ name: 'cf_clearance' });
await page.deleteCookie({ name: 'cf_chl_rc_ni' });

// Vider le Storage JS pour éviter la réutilisation des seeds JSD
const client = await page.target().createCDPSession();
await client.send('Storage.clearDataForOrigin', {
  origin: 'https://www.citaconsular.es',
  storageTypes: 'all'
});

```

#### B. Attendre le remplacement du cookie avant l'appel `/main/`

Dans vos logs :
`🔒 /main/ intercepté — attente JSD oneshot (max 6s)…`
`🔑 JSD oneshot resp: status=200 ... new-cf_clearance=❌ non`

Votre code intercepte et bloque la requête `/main/` **pendant** que le `oneshot` s'exécute. Mais comme le `oneshot` échoue (car le cookie `cf_clearance` n'est pas réémis), vous libérez `/main/` qui part immédiatement avec l'ancien cookie invalide, provoquant le `0B`.

**Correctif :**
Si `JSD oneshot resp` renvoie `new-cf_clearance=❌ non`, ne libérez pas la requête `/main/`. Annulez-la (`request.abort()`) ou rechargez la page d'accueil pour forcer Cloudflare à réémettre un challenge propre et générer un jeton `oneshot` avec un timestamp à jour.
