Cette documentation apporte **l'explication exacte et définitive** de ce qui se passe dans vos logs.

---

### La cause exacte : Vous tombez dans une règle Cloudflare `js_detection.passed`

1. **Génération initiale du `cf_clearance**`
Lorsqu'un utilisateur effectue une première requête HTML, Cloudflare injecte le script invisible `/cdn-cgi/challenge-platform/scripts/jsd/main.js` pour collecter des métriques. Si l'exécution réussit, Cloudflare émet le cookie `cf_clearance` en marquant en interne `js_detection.passed = true`.
2. **Le problème de décalage avec CapSolver**
Lorsque vous utilisez CapSolver, ce dernier génère un cookie `cf_clearance` sur **ses propres serveurs**. Mais quand vous l'injectez dans votre navigateur Chromium local, la session et le jeton JSD sont évalués par les règles WAF de Cloudflare.
Comme votre navigateur Puppeteer/Playwright présentait un décalage de signature (TLS, Client Hints `sec-ch-ua`, ou comportement de navigation), la vérification d'arrière-plan `oneshot` de JSD a échoué :
> `[spain-pb] 🔑 JSD oneshot resp: status=200 cf-ray=... new-cf_clearance=❌ non (rejeté ou pas d'upgrade)`


3. **La sanction : Le blocage silencieux sur `/main/**`
La documentation précise la stratégie recommandée par Cloudflare pour bloquer les bots :
> *"Vous devez activer les détections JavaScript, puis créer une règle WAF personnalisée à l'aide du champ `cf.bot_management.js_detection.passed`... L'action doit toujours être un défi géré ou un blocage."*


Lorsque votre navigateur effectue l'appel AJAX/XHR vers `/onlinebookings/main/...`, la règle WAF du serveur `citaconsular.es` évalue : `if (!cf.bot_management.js_detection.passed)`.
Au lieu d'afficher une page d'erreur visible, l'application coupe court et renvoie une réponse **200 OK avec 0 octet** (`0B snippet=""`).

---

### Résumé des enseignements clés

* **Le cookie `cf_clearance` seul ne suffit plus :** Il est réévalué en continu via les requêtes d'arrière-plan `/cdn-cgi/challenge-platform/.../oneshot/...`. Si le script JSD local échoue à valider l'empreinte du navigateur, `js_detection.passed` passe à `false`.
* **Les appels XHR/AJAX subissent la sanction :** Comme les requêtes AJAX ne réinjectent pas le script HTML de challenge, toute requête faite avec un statut `js_detection.passed = false` se fait filtrer ou vider par le WAF.

---

### La solution technique globale

1. **Alignement strict du User-Agent et des Client Hints :** Passez à Chromium le User-Agent exact fourni par CapSolver au lancement (`--user-agent="..."`) et surchargez les en-têtes CDP `Network.setUserAgentOverride` pour forcer des valeurs `sec-ch-ua` identiques (Chrome 135).
2. **Exécution du script JSD réel :** Laissez le navigateur exécuter naturellement la séquence de scripts `/cdn-cgi/challenge-platform/scripts/jsd/main.js` sur la page d'origine avant de déclencher l'action "Continuar".
3. **Alternative Web Unlocker :** Si l'alignement d'empreintes entre CapSolver et Chromium reste instable, l'utilisation d'un Web Unlocker (Oxylabs/Bright Data) en tant que proxy HTTP dans Playwright évitera les décalages, car l'Unlocker maintiendra la poignée de main TLS et le contexte JSD de manière transparente.
